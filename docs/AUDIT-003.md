# ТЗ №003 — регистрация и обязательная авторизация

## Реальные причины и результаты

Проверка `/auth/v1/settings`: email auth включён, signup разрешён, `mailer_autoconfirm=false`, anonymous users выключены. Ошибки параметров Project URL / publishable key не обнаружены. Прежний `signUp({email,password,options:{emailRedirectTo}})` использовал корректную сигнатуру SDK, однако:

- кабинет монтировался до проверки сессии и позволял работать с локальным гостевым прогрессом;
- форма находилась внутри кабинета, без имени, повторного пароля, полноценной валидации, подтверждения и resend;
- письма возвращают пользователя не на production URL: разрешённые Auth redirect URLs не настроены правильно;
- API письма восстановления при живой проверке вернул `429 email rate limit exceeded`; прежняя обработка не объясняла эту ошибку.

Проверочный `example.com` отклоняется Supabase как invalid email. Затем создан отдельный временный тестовый почтовый ящик, принадлежащий только этому тесту. Публичный signup вернул 200 и создал аккаунт без сессии. Письмо реально поступило, переход по настоящей ссылке подтвердил email (303), password login вернул 200. Имя найдено в `public.profiles`. Неправильный redirect подтверждён фактически, без изменения email confirmation settings.

Запрос recovery-письма получил 429. Поэтому получение recovery-письма не объявляется успешным. Отдельно реальным Supabase Auth admin generateLink выдан recovery token для временного пользователя; verifyOtp, updateUser(password) и вход новым паролем прошли. Это проверка настоящих Auth API без SMTP-доставки, а не доказательство получения reset-письма.

## Исправления

- `AuthGate` проверяет серверный getUser, подтверждение email и `mini_session_status` до монтирования кабинета. До этого доступны только загрузка и auth UI. Параметры `?screen=...`, старый локальный прогресс, просроченный или отозванный JWT не открывают кабинет.
- Вход, регистрация (имя/email/пароль/повтор), confirmation/resend, forgot-password и recovery callback вынесены в отдельный интерфейс. Валидация, русские ошибки, cooldown и 20-секундная граница ожидания.
- Оригинальная векторная графика: тропический ночной город, закат, неон и стеклянная панель; адаптивно, без заимствованных игровых ассетов.
- При выходе кабинет размонтируется сразу. Локальная отметка завершённой сессии предотвращает повторный вход старым сохранённым токеном на этом устройстве. RLS дополнительно проверяет реальное наличие `session_id` в `auth.sessions`: после успешного серверного logout старый ещё не истёкший JWT сразу лишается чтения и привилегированных RPC.
- Имя сохраняется metadata signup и безопасным trigger в profiles. Пользовательские metadata применяются только к отображаемому имени, не к авторизации.
- Mini App сохраняет существующую привязку и общий user_id. Без привязки — авторизация и явное связывание существующего аккаунта; новый Telegram-пользователь Supabase не создаётся автоматически.
- Данные аккаунта и очередь сохраняются под прежним ключом пользователя. Старый гостевой прогресс не удаляется: после входа доступно явное объединение с приоритетом текущих записей аккаунта. ErrorBoundary больше не экспортирует данные других локальных аккаунтов.
- Одноразовое security-обновление SW переводит открытые окна только этого PWA на новую авторизацию, сохраняя localStorage. При новом запуске без сети действующая сессия не считается подтверждённой: доступна auth-оболочка, кабинет закрыт.

## Проверки и границы доказательств

41 unit/PostgreSQL-тест, 13 Deno Edge-тестов, 28 Playwright сценариев desktop/mobile. Браузерные тесты auth state machine используют явно тестовые API-адаптеры; отдельные реальные API и production-проверки выполняются без них. TypeScript, ESLint и build обязательны в CI.

`docs/evidence/auth-api-003.json` — реальный signup, доставленное confirmation-письмо, подтверждение, login, profile name, logout и запрет старого JWT. `docs/evidence/live-audit-003.json` — реальные Supabase/Telegram API, включая сохранённую модель Mini App и reset API. Подписанный Telegram initData в этом наборе — серверный тестовый адаптер, не настоящий Telegram-клиент.

`scripts/production-browser-check.mjs` проверяет настоящий production URL. С `LIVE_AUTH_FILE` использует временный настоящий аккаунт: неверный пароль, вход, сохранение прогресса, reload, logout, повторное использование отозванного JWT. Файл с credential хранится только временно вне репозитория, содержимое не выводится. После проверки тестовые аккаунты удаляются.
